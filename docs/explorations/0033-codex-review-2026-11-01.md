# Codex review of decision 0033 and the entity catalog, 2026-11-01

One read-only round over the draft decision, the agreed points, the catalog research, decisions 0022 and 0026-0030 and the code at 4c2e932c. Every finding was taken into decision 0033.

**Part 1 — the decision**

1. **Blocking: partial reconciliation contradicts atomic publication.** `0033-draft.md:111–119`, Decision 18, allows the non-conflicting remainder of a transaction to pass. `0027-fill-orchestrator.md`, “Publication,” and `0028-temporal-graph-store.md`, “Publication,” require read revalidation and atomic publication of a unit generation. Element-wise conflict detection is insufficient: an unchanged edge may depend on a node, query result, or absence that changed.

   **Fix:** preserve the owner’s partial-progress requirement by partitioning the draft into dependency-closed publication units. Publish each accepted unit atomically, once, with its complete read set, generation, fence, cancellation check and durable result. Conflicted units receive replacement generations. Explicitly amend 0027/0028; do not say they simply “stand.”

2. **Blocking: agent supremacy has no compatible ownership mechanism.** `0033-draft.md:98–99,117–119,156` permits agents to remove, rename and merge extracted entities while asserting that 0028 stands. Under 0028, a producer normally changes only its own versions; agent interpretations remain distinguishable from deterministic relations. The current publisher enforces ownership in [publish.ts](src/graph/publish.ts:194).

   **Fix:** define corrections as a separate, durable overlay: target identity and revision digest, operation, basis, authoring agent and supersession links. Preserve the raw extraction. Specify how reads combine assertions and corrections, how suppressions survive re-extraction, and how invalidated corrections re-enter verification. Node merges must follow 0028’s predecessor/new-identity rule, including endpoint reconciliation. Amend the interpretation rule explicitly.

3. **Blocking: the branch layer has no temporal or publication contract.** `0033-draft.md:131–136,156–158` adds branches without extending 0028’s `{valid, known, state}` read context or its producer/scope/generation identity. Architecture state cannot silently double as branch identity. Otherwise two branches can collide in publication keys or accidentally read each other’s facts.

   **Fix:** define an explicit branch/workspace context, immutable base commit, overlay revision and independently fenced publication namespace. Specify shadowing, tombstones, deletion, rename, rebase, force-push, branch removal and garbage collection. Every traversal, cache key, tracked read and correction must carry that context. Keep default-branch valid time governed by 0028; record when branch evidence was learned separately.

4. **Blocking: merge-base inheritance and verification transfer are unsafe as written.** `0033-draft.md:131–135` assumes a usable graph at the merge-base. Under `0030-fill-the-tip-first-history-from-git.md`, that structure may never have been extracted. Moreover, unchanged branch files can acquire different meaning through changed imports, configuration, schema, dependency resolution or build settings.

   **Fix:** materialize the merge-base as a chosen point when absent. Overlay changed files and invalidate their dependency closure, including query membership and negative reads. At merge, transfer a verification certificate only when its entire evidence and dependency digest remains equivalent in the actual merged tree. Rebind it to the merge publication; preserve the original branch verification provenance. Comparing only directly changed elements is insufficient.

5. **Blocking: “nobody edits by hand” still permits loss of a person’s knowledge.** `0033-draft.md:85–87,141–148,157` preserves interpreted intent but does not require saving the original statement before interpretation. A failed session, mistaken paraphrase, correction overwrite or rebuild can lose it. This does not resolve `0029-knowledge-in-markdown-graph-as-index.md`, “Where data lives” and “People edit source entities,” which protect irreproducible human knowledge. Agreed points 22, 23 and 26 require attribution and document grounding.

   **Fix:** durably record the person’s original text, identity, timestamp and conversation/document reference before scheduling interpretation. Link resulting intent, disagreements and tasks to that record. Retraction and supersession must preserve history. A person’s intended constraint must remain visible when code contradicts it; code evidence must not erase intent. Require an acknowledgement showing exactly what was retained, plus replay after interruption.

6. **Blocking: the verification walk has no termination rule.** `0033-draft.md:95–107,127–135` combines top-down verification, parent confirmation down to code, agent-created nodes and continuous updates. Cyclic dependencies, shared descendants, repeated regrouping and disagreements can continually regenerate work. Context exhaustion terminates a turn, not the workflow.

   **Fix:** pin each verification epoch to a graph/input revision; persist a frontier and certificates keyed by entity revision and verifier configuration. Visit shared descendants once per applicable dependency revision. Condense cycles or verify their strongly connected components together. Bound discovery/reconciliation iterations and retries; unresolved cases become blocked questions. Close an epoch with explicit complete/partial coverage before admitting later commits into another epoch.

7. **Blocking: universal verification has no credible affordability contract.** `0033-draft.md:98–107,127–140` inherits unit limits but supplies no first-fill cost target, denominator or policy when budgets expire. For illustration—not a measurement—20,000 symbols with five relevant edges each already means roughly 120,000 symbol/edge verdicts, before files and higher-level entities. At 50 items per batch that is 2,400 batches; ten seconds per batch is about 6.7 serial hours. Rich evidence and escalations increase this.

   **Fix:** retain verification of every element as the coverage goal, with explicit token, monetary, call, elapsed-time and concurrency budgets. Define batching, evidence reuse, certificate reuse, ageing and resumable partial completion. Publish verified/static/stale/disputed counts against a pinned denominator. Count jev verdicts with their actual verifier identity and evidence; define whether they satisfy “agent verified.” Never report budget exhaustion as full verification.

8. **The proposed checks would catch some bypasses, but not the Context’s central defect.** `0033-draft.md:47–52` does not detect a reachable whole-tree extractor rebuilding a global table for every file. That implementation can have one writer and one entry point and obey every import rule. The offending loop is confirmed in [resolve.ts](src/extract/code/resolve.ts:62), called per file from [index.ts](src/extract/code/index.ts:355). The tree reader also loads all blobs on its first read: [git.ts](src/extract/driver/git.ts:167).

   **Fix:** add enforceable capability boundaries: static workers receive one file’s bytes and bounded graph-query interfaces, never a whole-tree reader or repository-wide semantic object. Use AST/type-aware checks for forbidden capabilities and connection/query access. Explicitly prohibit entry surfaces from starting alternative runners. Keep reachability checks, but distinguish their guarantees from resource-complexity acceptance. [Dependency-cruiser documents dependency rules](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md), not a proof of algorithmic complexity.

9. **Several owner-agreed requirements are missing or weakened.** In `0033-draft.md`:

   - **Agreed 23:** line 146 requires permission to *create* a divergence work item. The agreement creates and shows it automatically; permission is required before assigning execution. Separate detection, recording and execution.
   - **Agreed 29/31:** lines 82–84 allow roles to lead areas only; omit subgroup selection and starting the conversational agent from the person’s role groups. Add both.
   - **Agreed 9:** lines 95–105 omit dependencies between entity kinds. Declare and validate discovery dependencies separately from navigation relationships.
   - **Agreed 25:** lines 65–79 omit the agent noting where an unimplemented kind would apply. Require applicability findings without pretending extraction exists.
   - **Agreed 21:** lines 137–140 omit the explicit shared-queue/multiple-machine execution contract and worker replacement after crashes or leaks. State ownership, fencing, admission and restart behavior.
   - **Agreed 3/8:** lines 53–56 delete existing agent stages without explicitly requiring writer units and useful stages 8–13 to become registry stages. Name their replacements and preserved responsibilities.
   - **Agreed 26:** document origin is named, but source-section grounding of intended statements is not explicit. Require document revision, section and evidence span.

10. **“Confirmed down to code” cannot apply to every catalog kind.** `0033-draft.md:103–105` cannot verify planned requirements, strategic goals, research observations, legal obligations or an undeveloped product by finding implementation. It also risks circularly treating code-derived intent as evidence that implementation satisfies intent.

    **Fix:** distinguish verification of an assertion’s evidence from implementation conformance. Intent can be faithfully recorded and verified against a person/document while remaining unimplemented or contradicted. Require independent intended-to-implemented mappings. Keep proposed, human-accepted and agent-verified statuses separate, preserving 0026’s three distinct checks and 0028’s digest-bound acceptance.

11. **States and invalidation are underspecified.** `0033-draft.md:117–123` invalidates changed elements, but an unchanged claim can become unsupported when a dependency disappears, an empty query gains a result, a correction changes or a verifier rule changes. The four labels also cannot adequately express verified intention awaiting implementation, refuted assertions or accepted risk.

    **Fix:** version verification separately from assertion content. Track complete dependencies, including negative reads and query membership, as 0027 requires. Separate freshness, verification outcome, provenance, human acceptance and lifecycle into independent dimensions. Define filtering of edges whose endpoints are hidden and whether page coverage includes hidden/unimplemented kinds.

12. **Graph-only notes conflict with the rebuild promise unless narrowly defined.** `0033-draft.md:108–110,117–119,157` persists correction bases but leaves confirmation grounds, suspicions, handoffs and summaries only in the graph. Some of these contain non-reproducible agent knowledge protected by 0029.

    **Fix:** identify which records are disposable execution checkpoints and which are durable assertions, disputes or evidence. Persist the latter in the product repository. Define whether verification certificates survive rebuilding; if they do, retain their evidence/configuration digests durably and revalidate them before reuse. State explicitly what a rebuild loses.

13. **The full catalog is neither complete nor ready as starter data.** `0033-draft.md:60–79` claims completeness while naming areas still requiring research. `entity-catalog-research.md` has grouped prose rows, unverified references and no canonical per-kind identifiers, origin-capability records or subgroup assignments. Agreed points 24–27 and 31 require the full catalog now.

    **Fix:** replace “complete” with a precise acceptance scope, incorporate the omissions in Part 2, and normalize the catalog into reviewable data. Each kind needs an identifier, definition, area/subgroup, sources, supported acquisition methods, implementation status, relation constraints and template policy. Validate these mechanically; keep unsupported acquisition methods explicit.

14. **The extractor/product namespace boundary disappears from the proposal.** `0033-draft.md:60–79,91–105,152–156` can be read as making catalog kinds the extractors’ schema. Both 0026 and `0028-temporal-graph-store.md`, “Tables,” explicitly require separate extractor and product vocabularies with mappings; products may remove catalog kinds without changing what code extraction observes.

    **Fix:** retain both namespaces and declare versioned mappings. Product removal affects product views or interpretation, not retention of raw evidence. Define multiple mappings, unmapped facts and relation semantics. Standard names from SPDX, Backstage and C4 are not interchangeable merely because their labels resemble each other.

15. **Storage centralization needs a transaction boundary, not only interfaces.** `0033-draft.md:43–46,137–140` does not say how graph, workflow state and queue interfaces participate in the single owner transaction required by 0027. Separate IPC calls could publish knowledge and crash before settling work. Multiple machine-local owners also need a clear relationship to shared PostgreSQL authority.

    **Fix:** expose an owner-side atomic publication operation spanning all three stores and its durable events/outbox. Define one embedded-database owner locally and globally fenced publication authority over shared PostgreSQL. Workers submit drafts through that boundary. Budget the database, queues, IPC buffers and retained results as well as workers; one very large file still requires a size/output policy.

16. **0022’s extension boundaries need an explicit disposition.** `0033-draft.md:36–46,141–160` expands “every job” and future autonomous execution without restating `0022-architecture-extension-points.md`’s single accepted-write/event path and external executor boundary. Internal fill orchestration and external development/deployment execution are different responsibilities.

    **Fix:** say whether 0022’s external executor contract remains. Route conversational writes and corrections through the same authored write path, with durable events and idempotent Git publication. If execution ownership moves into madarch, amend 0022 explicitly rather than relying on “builds on.”

17. **The migration inventory omits an existing verification surface.** `0033-draft.md:25–27,53–56` lists staged agents and the writer, but [graph-verdicts.ts](src/knowledge/graph-verdicts.ts:1) already implements deterministic checks, jev/classification/analysis escalation, budgets and evidence/configuration caches outside the proposed workflow. This needs explicit migration or deletion alongside the other runners.


    **Fix:** provide a responsibility-to-replacement inventory covering extraction, writing, verification, indexing, publication and recovery. Reachability alone cannot identify an architecturally redundant path that remains actively called.

18. **Correct the source references and qualify the incident evidence.** `0033-draft.md:20,53` names `src/extract/driver`, but the current implementation is a directory, with its entry at [driver/index.ts](src/extract/driver/index.ts:60). The principal code diagnosis is supported: [fill-worker.ts](src/knowledge/fill-worker.ts:295) calls that driver and separately calls [runWriter](src/knowledge/fill-worker.ts:541); the staged orchestrator initializes the old [fact store](src/fill/orchestrator-host.ts:396).

    The VM failures, benchmark figures and attribution to an earlier task at draft lines 14–30 are not established by source inspection alone. **Fix:** link the incident/measurement record, input revision and measurement method; distinguish measured heap from peak process/VM memory. Do not present these figures as independently verified by this review.

**Part 2 — the catalog’s completeness**

1. **Correct the acquisition model first.** `entity-catalog-research.md:11–13` defines “no” as having no repository representation, then applies it to entities explicitly available in documents. A repository can contain strategy, research, incident, privacy and operational records; source code alone cannot establish their truth.

   In the additions below, **structured** means deterministic extraction from committed formats; **document** means extraction from authored records with attribution; **external** means actual observations require an imported source record. These describe possibilities, not existing madarch support. Named graph specializations should be identified as catalog design choices where the source defines the underlying artifact rather than an ontology class.

2. **Resilience and continuity are absent as a developed area.** Beyond the draft’s proposed additions, include **business-impact analysis, critical business process, maximum tolerable downtime, recovery priority, continuity plan, disaster-recovery plan, activation criterion, recovery procedure, reconstitution procedure, recovery team, alternate processing site, alternate storage site, contingency exercise and exercise result**. Model RTO/RPO as traceable recovery objectives. Sources: [NIST SP 800-34](https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-34r1.pdf) and [SP 800-53, CP controls](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final).

   Also include **backup policy, backup plan/job, backup artifact/recovery point, backup vault/location, restore operation, restore-validation result, replication configuration, regional replica, failover/failback procedure and recovery test result**. A replica is not proof of a usable backup. [AWS reliability guidance](https://docs.aws.amazon.com/wellarchitected/2022-03-31/framework/rel-failmgmt.html) defines backup/recovery practices.

   **Repository yield:** structured policies/IaC and document plans; actual backup completeness, replication lag and achieved recovery results require external evidence.

3. **FinOps is missing.** Add **billing account/subaccount, cost-and-usage record, charge, pricing/SKU reference, commitment discount, contract commitment, allocation rule, allocation target/cost centre, shared-cost allocation, budget, forecast, cost anomaly, unit-cost measure, optimization recommendation and savings outcome**. These connect expenditure to products, environments, owners and decisions. Sources: [FOCUS cost-and-usage schema](https://focus.finops.org/docs/specification/v1-3/datasets/cost-and-usage/) and the [FinOps Framework](https://www.finops.org/framework/).

   **Repository yield:** structured tagging, budgets and allocation policies when committed; billing, utilization, forecasts and realized savings usually require external imports. Do not confuse resource limits with spending budgets.

4. **Vendor and third-party management is missing beyond package dependencies.** Add **supplier/vendor, supplied product/service, supplier assessment, supply-chain risk assessment, acquisition agreement, contractual security requirement, supplier dependency/tier, supplier assurance evidence and supplier monitoring/reassessment**. Capture contract renewal/termination and exit obligations as agreement attributes or linked work. [NIST SP 800-161r1](https://csrc.nist.gov/pubs/sp/800/161/r1/upd1/final) supplies the acquisition and supplier-risk framework.

   **Repository yield:** document agreements and assessments, structured declared suppliers; operational performance and current contractual status need imported evidence. An external-system node does not represent the supplier agreement.

5. **Decommissioning is missing.** Add **retirement decision, retirement plan, end-of-support/sunset notice, replacement service, consumer migration, data-transfer/archive disposition, disposal operation, sanitization record and sanitization certificate**. Sources: the [GOV.UK retirement guidance](https://www.gov.uk/service-manual/agile-delivery/how-the-retirement-phase-works), [RFC 8594](https://www.rfc-editor.org/info/rfc8594/) and [NIST SP 800-88r2](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-88r2.pdf).

   **Repository yield:** document plans/notices and structured sunset configuration; completion, revoked access, deleted resources and sanitization require external evidence. A `retired` lifecycle label alone cannot establish safe disposal.

6. **Privacy coverage stops far short of processing records.** In §13, add **legal basis, consent record/withdrawal, controller, processor, joint-controller arrangement, processing agreement, privacy notice, data-subject right/request, request response, DPIA, privacy-risk assessment, transfer safeguard, personal-data breach, breach notification, retention/deletion policy and deletion evidence**. Sources: the [DPV vocabulary](https://w3c.github.io/dpv/2.0/dpv/), [DPVCG’s risk and breach vocabularies](https://www.w3.org/community/dpvcg/) and [EDPB legal-basis guidance](https://www.edpb.europa.eu/topics/key-gdpr-concepts/legal-basis_en).

   **Repository yield:** document policies, agreements and assessments; structured consent/request exports and deletion receipts can be imported. Code can expose processing paths; it cannot establish consent or legal justification. Represent these as restricted metadata/evidence links where appropriate.

7. **Security needs response and operational assurance, not only scan outputs.** Extend §12 with **vulnerability disclosure policy, vulnerability report, triage decision, remediation record, security advisory and disclosure communication**; these are distinct from CVE and SARIF findings. [NIST SP 800-216](https://csrc.nist.gov/pubs/sp/800/216/final) defines the disclosure workflow; [RFC 9116](https://www.rfc-editor.org/rfc/rfc9116.html) defines machine-readable reporting contacts.

   Add **audit policy, audit event, security exception/risk acceptance, access review and credential/key lifecycle policy** under the relevant security controls. Sources: [NIST SP 800-53](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final) and [Kubernetes audit records](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/).

   **Repository yield:** structured policies/configuration and document decisions; actual access, rotation, review and remediation evidence require external records.

8. **Threat intelligence and detection are missing specializations.** Add **attack pattern, indicator, observed data, sighting, intrusion set/campaign where relevant, course of action and threat-intelligence report**. A generic “threat” cannot retain their different semantics. [STIX 2.1](https://docs.oasis-open.org/cti/stix/v2.1/os/stix-v2.1-os.html) defines these object types.

   **Repository yield:** structured STIX bundles and committed detection content; sightings and observed attacks require imports. These are optional security subgroups, not mandatory instances for every product.

9. **Data governance needs more than datasets and lineage facets.** Extend §7 with **data catalog, catalog record, dataset series/version, distribution, data service, access service, data-quality metric, quality measurement, quality annotation and quality policy**. Sources: [DCAT 3](https://www.w3.org/TR/vocab-dcat-3/) and [DQV](https://www.w3.org/TR/vocab-dqv/).

   Add explicit **provenance activity, responsible agent, derivation and attribution records** using [PROV-O](https://www.w3.org/TR/prov-o/). OpenLineage job/run records can map into these; they should not replace provenance for documents, decisions and agent corrections.

   **Repository yield:** structured catalog/schema/quality files and document governance; observed lineage and quality measurements need execution evidence.

10. **ML/AI is a placeholder, not a lifecycle model.** §17’s model/dataset/training-run row omits **model version, registered model, model alias, experiment grouping, run parameter, metric observation, model artifact/checkpoint and evaluation result**. [MLflow Tracking](https://www.mlflow.org/docs/latest/tracking/) and its [registry](https://mlflow.github.io/mlflow-website/docs/latest/ml/model-registry/) define these records.

    Add **typed artifact, execution, execution context and input/output lineage event** from [ML Metadata](https://www.tensorflow.org/tfx/guide/mlmd). For generative AI, add **prompt template/version, evaluation dataset, scorer/judge and evaluation result** from the [MLflow GenAI API](https://mlflow.org/docs/latest/api_reference/python_api/mlflow.genai.html). Add **AI impact/risk assessment, monitoring evaluation and decommissioning decision** based on [NIST AI RMF](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/).

    **Repository yield:** structured configurations, cards and prompts; trained artifacts and evaluations require retained run evidence. Keep model metadata distinct from raw weights and training data.

11. **Incident response lacks its operational record.** §11 includes incident/postmortem/action item, but lacks **incident-role assignment, incident command record, status update, response timeline event, operational handoff and mitigation/recovery action**. These connect people and decisions to what happened, rather than leaving them inside one opaque document. Sources: [Google’s incident-response model](https://sre.google/workbook/incident-response/) and [NIST SP 800-61r3](https://csrc.nist.gov/pubs/sp/800/61/r3/final).

    **Repository yield:** document playbooks and exported incident records; actual response events require imports. Preserve incident commander, operations and communications responsibilities separately.

12. **Operations needs planned work and actual execution.** Beyond generic runbooks, include **maintenance plan/window, maintenance execution, operational change request, change approval, configuration baseline and configuration-change record**. [NIST SP 800-53’s CM and MA controls](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final) define these concerns.

    **Repository yield:** structured desired configuration and document plans/approvals; actual execution and drift require external evidence. Also distinguish an **error-budget policy** from the error-budget value already listed; the former governs release/operational decisions.

13. **Observability omits the collection and notification architecture.** Extend §11 with **telemetry pipeline, receiver, processor, exporter, connector, sampler and instrumentation scope/configuration**. Sources: [OpenTelemetry Collector configuration](https://opentelemetry.io/docs/collector/configuration/) and the [Tracing SDK](https://opentelemetry.io/docs/specs/otel/trace/sdk/).

    Add **alert instance, notification route, receiver, inhibition rule and silence**; an alert-rule definition is not an occurrence or a suppression. [Alertmanager](https://prometheus.io/docs/alerting/latest/configuration/) defines these.

    **Repository yield:** structured configuration; actual alerts, delivery outcomes and telemetry observations need imports. Keep high-volume telemetry in its source system and retain useful indexed evidence references.

14. **Release and deployment need gates and rollout evidence.** Extend §9 with **deployment approval/protection rule, approval decision, deployment status, rollout strategy/step, analysis template, analysis run, promotion and rollback operation**. Sources: [GitHub protection rules](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments), [deployment statuses](https://docs.github.com/en/rest/deployments/deployments) and [Argo Rollouts analysis](https://argoproj.github.io/argo-rollouts/features/analysis/).

    **Repository yield:** structured rules and rollout plans; actual approvals, analysis, promotion and rollback require external records. A release, deployment request and running deployment are separate things.

15. **Build and supply-chain records need explicit internal objects.** §9/12/17 mention these schemas but often leave their objects inside prose. Promote **build definition, build invocation, builder/build platform, resolved input/dependency, build output/byproduct, attestation subject, predicate and signature/verification result** to explicit supported kinds or documented members. Use [SLSA provenance](https://slsa.dev/spec/v1.0/provenance) and [in-toto attestation](https://github.com/in-toto/attestation/blob/main/spec/README.md).

    **Repository yield:** structured build definitions and committed attestations; actual invocations and signatures need retained build records. A workflow configuration does not prove that an execution achieved a SLSA level.

16. **Code review is missing as a first-class activity.** §16 names PRs and a `reviewedBy` relation, but lacks **review request, review submission, review comment/thread, suggested change, approval, changes-requested decision and dismissal**. Reviews are revision-bound records, not merely edges from a PR to a user. Sources: [GitHub review records](https://docs.github.com/en/rest/pulls/reviews) and [review comments](https://docs.github.com/en/rest/pulls/comments).

    **Repository yield:** generally external forge imports; Git objects alone do not contain the complete review. Preserve reviewed commit/diff positions and outdated/dismissed status.

17. **Checks and compatibility decisions are missing from testing.** Add **check suite, check run and check annotation**, distinct from pipeline runs and test cases. [GitHub Checks](https://docs.github.com/en/rest/checks/runs) defines their revision, result and location data.

    Add **consumer/provider version, contract verification result and deployment-compatibility decision** for consumer-driven contracts. [Pact Broker](https://docs.pact.io/pact_broker/overview) and [Can I Deploy](https://docs.pact.io/pact_broker/can_i_deploy) define those records.

    **Repository yield:** structured contract files/configuration; actual check and compatibility outcomes need retained reports/imports. The existing generic test-result kind can be reused through explicit specialization.

18. **Performance and capacity are underdeveloped.** §17 has budget/benchmark, but needs **workload scenario, load profile, executor configuration, threshold, performance measurement/baseline and regression comparison**. [k6 scenarios](https://grafana.com/docs/k6/latest/using-k6/scenarios/) and [thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/) supply concrete definitions.

    Add **capacity model, demand forecast, capacity limit/headroom and overload policy** based on [Google’s capacity-management guidance](https://sre.google/static/pdf/login_winter20_10_torres.pdf). For resilience testing, distinguish **fault experiment, fault specification, schedule and experiment result** using [Chaos Mesh](https://chaos-mesh.org/docs/create-chaos-mesh-workflow/).

    **Repository yield:** structured test/configuration artifacts and document models; measurements, saturation and achieved capacity require observations. These can specialize existing experiment/metric kinds.

19. **Architecture lacks behavior and architecture-description entities.** §5 should explicitly include **state machine, state, transition, trigger, guard, activity/action, interaction and message** from [UML](https://www.omg.org/spec/UML/2.5.1). Include **business process, process activity, event, gateway, participant/lane and sequence/message flow** when BPMN is used; [BPMN 2.0.2](https://www.omg.org/spec/BPMN/2.0.2) defines them.

    Add **architecture viewpoint, stakeholder concern, model kind, correspondence and correspondence rule**; “arc42 views” is not their replacement. [ISO/IEC/IEEE 42010](https://www.iso.org/standard/74393.html) defines the architecture-description framework.

    **Repository yield:** structured UML/BPMN/model files; code can yield candidate behavior, not automatically the intended model. This also closes the owner’s explicitly requested state-machine gap.

20. **Idea and strategy need a fuller business model.** §1 conflates several existing terms and omits explicit **mission, strategy, tactic, influencer and business-policy specializations** from the [OMG Business Motivation Model](https://www.omg.org/spec/BMM/1.3/PDF). Preserve their distinctions from goal, objective, assessment and course of action already listed.

    **Repository yield:** document strategy/model files; structured extraction is possible from a declared BMM representation. They cannot be inferred reliably from implementation alone.

21. **Discovery and research lack their evidence-producing process.** Extend §3 with **research plan, research question, research round/session, participant/recruitment criterion, discussion guide, consent record, observation and research-data artifact**. Generic experiment/finding nodes omit how evidence was obtained. Sources: [GOV.UK research planning](https://www.gov.uk/service-manual/user-research/plan-round-of-user-research) and [informed-consent guidance](https://www.gov.uk/service-manual/user-research/getting-users-consent-for-research).

    **Repository yield:** document plans, guides and appropriately retained evidence metadata; session observations and consent require authored/imported records. Link findings to observations rather than presenting agent summaries as primary evidence.

22. **Requirements need change and assurance records.** Add **requirements baseline, requirements change request, change-impact assessment and approval/waiver decision** as controlled-document/change specializations under [NIST configuration-management controls](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final). For products needing structured assurance, add **assurance case/package, claim, argument reasoning and artifact reference** from [OMG SACM](https://www.omg.org/spec/SACM/2.3).

    **Repository yield:** document or structured records; code supplies supporting evidence, not acceptance or authority. A test link alone does not represent an argument that a requirement has been satisfied.

23. **Accessibility needs the evaluation model.** §4/17 list criteria and conformance reports, but omit **ACT rule, applicability condition, expectation, evaluation assertion, assertor, test subject, evaluation result and evaluation mode**. Sources: [ACT Rules Format 1.1](https://www.w3.org/TR/act-rules-format-1.1/) and [EARL](https://www.w3.org/TR/EARL10-Schema/), the latter a Working Group Note.

    **Repository yield:** structured rules/reports; manual and assistive-technology evaluation requires authored observations. A WCAG conformance claim must identify its scope and satisfy [whole-page and complete-process requirements](https://www.w3.org/TR/WCAG22/#conformance-reqs); passing automated checks is insufficient.

24. **Localization needs translation workflow and locale behavior.** §4/17 include messages and locales but omit **translation unit, segment, source/target variant, translation/review state, translation candidate and terminology/glossary entry** from [XLIFF 2.1](https://docs.oasis-open.org/xliff/xliff-core/v2.1/xliff-core-v2.1.html). Add traceable **locale fallback/inheritance and formatting/plural/collation rules** where product behavior depends on them; [Unicode TR35](https://www.unicode.org/reports/tr35/tr35.html) defines the underlying data.

    **Repository yield:** structured XLIFF/locale resources and configuration; translation acceptance needs retained review evidence. Message keys alone cannot show approved translation coverage.

30. **Fix grouping and the distinction between kinds, properties and relationships.** ADRs belong in architecture/decision governance with R&D links; provenance is cross-cutting; accessibility and localization merit navigable subgroups; continuity, FinOps, supplier management and retirement need explicit placement.
